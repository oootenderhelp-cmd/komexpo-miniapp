# Лид-модуль DAREMA

Модуль генерации и обработки заявок для сети стоматологических клиник DAREMA
(Санкт-Петербург) внутри платформы Komexpo.

## Что делает

1. **Форма записи** (`/dental`) — публичная страница: пациент выбирает
   направление, описывает жалобу, оставляет контакты и отмечает согласия.
2. **Рейтинг срочности** — каждая заявка получает балл 0–100 и приоритет.
   Тому, у кого острая боль и готовность приехать сегодня, звонят первым.
3. **Кабинет** (`/dental/leads`) — очередь на связь, отчёт по дням, разрез по
   кампаниям, смена статусов, подготовка первого сообщения в мессенджер.
4. **Контроль SLA** — просроченные заявки видны сами: счётчик в шапке, красная
   подпись в очереди, фильтр «только просроченные», колонка в выгрузке.
5. **Оповещение администраторов** — на критичную и срочную заявку падает
   уведомление в кабинет, чтобы 15 минут не утекли в обновление вкладки.
6. **Выгрузка в Excel** — сводка по дням, общий лист и вкладка на каждый день.

## Правовая рамка

Это не парсер. Модуль намеренно не умеет собирать контакты из соцсетей,
чатов, пабликов и чужих сайтов, и добавлять такую возможность в него нельзя.

Причина простая: жалоба на зубную боль — это сведения о состоянии здоровья,
особая категория персональных данных (ст. 10 152-ФЗ). Собирать её без согласия
нельзя, а рассылать по такой базе рекламу — отдельное нарушение ст. 18 38-ФЗ.
Ответственность ложится и на клинику, и на подрядчика по лидам.

Что вместо этого:

| Требование | Как закрыто |
|---|---|
| Основание для хранения контактов | Галочка согласия на обработку ПД, без неё заявка не принимается (`consentPd: z.literal(true)`) |
| Основание для сообщения в мессенджер | Отдельная галочка на коммуникации, проверяется в `canContact()` |
| Отзыв согласия | Страница `/dental/opt-out` и процедура `dental.optOut` по номеру заявки: ставит `optedOut` и гасит право писать |
| Фиксация согласия | `consentAt`, `consentText` — версия текста, под которым подписался пациент |
| «Где поймали» | UTM-метки кампании, а не данные о человеке |

Ник мессенджера сохраняется только вместе с согласием на переписку: если
галочки нет, канал принудительно сбрасывается в `none` ещё на входе, чтобы в
базе не оказалось контакта, писать на который права нет.

## Рейтинг срочности

Формула открытая и линейная — менеджер должен понимать, почему заявка наверху
списка, иначе он ей не верит и звонит в своём порядке.

```
балл = база направления
     + уровень боли × 3
     + два самых тяжёлых симптома
     + готовность прийти
```

| Балл | Приоритет | SLA первого касания |
|---|---|---|
| 70–100 | Критично | 15 минут |
| 45–69 | Высокий | 1 час |
| 20–44 | Средний | 8 часов |
| 0–19 | Низкий | 24 часа |

Симптомы считаются по двум самым тяжёлым: иначе длинная анкета механически
перевешивает реальную остроту, и «кровоточивость + выпала пломба + эстетика»
обгоняет флюс.

Каждая заявка хранит `urgencyReasons` — расшифровку, из чего сложился балл.

## Контроль SLA

Обещанное время первого касания считается от момента заявки: критичная — 15
минут, высокая — час, средняя — 8 часов, низкая — сутки.

Часы останавливаются в момент касания (`firstTouchAt`) или при закрытии заявки,
а не тикают до бесконечности: заявка, по которой связались на пятой минуте,
навсегда остаётся уложившейся в срок, даже если открыть её через неделю.
Заявка, закрытая как спам, просроченной не считается.

Правило живёт в двух местах и берёт минуты из одного словаря
`URGENCY_SLA_MINUTES`: `getSlaState()` — для интерфейса и выгрузки,
SQL-выражение в `dentalLeadConditions()` — для фильтра «только просроченные»,
чтобы база и кабинет не разъехались.

## Счётчики

Подключаются только на страницах DAREMA и только если заданы переменные:

```
VITE_YANDEX_METRIKA_ID=
VITE_VK_PIXEL_ID=
```

Пиксель VK нужен для ретаргетинга и оценки кампаний: сегмент собирается на
стороне рекламной системы, списки людей к нам не выгружаются. В цель
`dental_lead` уходит только факт заявки и направление, без контактов пациента.

## Структура

```
shared/dental.ts              каталог услуг, скоринг, шаблоны, canContact()
server/lib/xlsx.ts            генератор .xlsx без внешних зависимостей
server/lib/leadExport.ts      сборка книги: отчёт + общий лист + вкладки по дням
server/routers/dental.ts      tRPC: приём заявок, кабинет, выгрузка
server/db.ts                  доступ к таблицам dental_leads / dental_lead_events
client/src/pages/dental/      форма записи, кабинет, отзыв согласия
client/src/components/dental/ счётчики Метрики и пикселя VK
drizzle/0003_*.sql            миграция
```

### API

| Процедура | Доступ | Назначение |
|---|---|---|
| `dental.services` | публично | каталог направлений |
| `dental.submitLead` | публично | приём заявки с формы |
| `dental.optOut` | публично | отзыв согласия по номеру заявки |
| `dental.list` | admin / owner | очередь заявок с фильтрами |
| `dental.byId` | admin / owner | карточка и история касаний |
| `dental.dailyStats` | admin / owner | сводка по дням |
| `dental.campaignStats` | admin / owner | разрез по каналам и кампаниям |
| `dental.overdueCount` | admin / owner | сколько заявок просрочено по SLA |
| `dental.setStatus` | admin / owner | движение по воронке |
| `dental.firstTouchMessage` | admin / owner | текст первого сообщения |
| `dental.markContacted` | admin / owner | фиксация касания |
| `dental.exportXlsx` | admin / owner | выгрузка книги Excel |

`firstTouchMessage` только готовит текст. Отправляет менеджер сам, из своего
аккаунта: автоматической рассылки в модуле нет и по описанной выше причине быть
не должно.

## Выгрузка в Excel

Книга собирается своим генератором (`server/lib/xlsx.ts`) — zip с XML внутри,
на `node:zlib`, без внешних пакетов.

- **Отчёт по дням** — дата, число лидов, разбивка по срочности, записаны,
  дошли, конверсия в приход.
- **Все лиды** — 27 колонок: контакты, канал, ник, услуга, срочность и её
  расшифровка, симптомы, источник и кампания, согласия, статус, даты.
- **Вкладка на каждый день** — те же колонки, только заявки этой даты.

Сутки считаются по Europe/Moscow: заявка в 01:30 мск попадает в свой день, а не
во вчерашний по UTC. Вкладок не больше 60; если дней больше, лишние остаются
только на общем листе, и выгрузка об этом прямо сообщает (`omittedDays`).

## Запуск

```bash
pnpm install
# в .env: DATABASE_URL=mysql://...?charset=utf8mb4
pnpm db:push     # применит drizzle/0003_*
pnpm dev
```

Форма — `/dental`, кабинет — `/dental/leads` (нужна роль `admin` или `owner`).

Ссылка из объявления может вести сразу на нужное направление и нести метки:

```
/dental?service=implantaciya&utm_source=vk&utm_medium=cpc&utm_campaign=spb_implant&utm_content=banner_1
```

## Что осталось согласовать с клиникой

- Точный перечень направлений и их названия — сейчас в каталоге стандартный
  набор из 10 направлений, его нужно сверить с прайсом DAREMA.
- Лид-магнит по каждому направлению: бесплатная диагностика, снимок, подбор
  врача — что клиника реально готова давать.
- Текст согласия на обработку ПД (сейчас помечен версией `dental-v1`) и
  политика обработки — их готовит юрист клиники, модуль только фиксирует, под
  какой версией подписался пациент.
- Адреса клиник и график: в первом сообщении обещается приём в день обращения,
  это должно быть правдой.
