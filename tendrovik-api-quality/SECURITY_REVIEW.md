# SECURITY REVIEW — Тендровик AI

Ревизия безопасности backend-модуля `tendrovik-backend`.
Статус: **фаза foundation** (HTTP-сервер ещё реализуется Codex).

Версия документа: 2026-08-02.

---

## 1. JWT / RBAC

| # | Проверка | Статус | Комментарий |
|---|----------|--------|-------------|
| 1.1 | Bearer JWT описан в OpenAPI (`securitySchemes.bearerAuth`) | ✅ Описан | Все маршруты требуют `security: [bearerAuth]` |
| 1.2 | JWT-проверка реализована в middleware | ❌ Не реализовано | Нет middleware: любой запрос проходит. **Критично.** |
| 1.3 | Срок жизни токена (exp) и refresh | ❌ Не реализовано | Необходимы: exp ≤ 1h для access, refresh ≤ 7d |
| 1.4 | RBAC на основе таблиц `roles`, `permissions`, `user_roles` | ⚠️ Схема есть | Таблицы созданы в Drizzle; проверки в хендлерах отсутствуют |
| 1.5 | Разграничение прав по ролям (сметчик/юрист/тендеровик/владелец) | ⚠️ Логика есть | `approvals.ts` проверяет роль при `signStep`; HTTP-слой не ограничивает |
| 1.6 | Отзыв токена (logout / blocklist) | ❌ Не реализовано | При реализации: Redis/DB blocklist |

**Рекомендация:** реализовать JWT middleware первым — до запуска сервера в сеть. Алгоритм: RS256 или EdDSA (не HS256 для прод). Хранить публичный ключ в env/файле, не в коде.

## 2. Мультиарендность (workspace isolation)

| # | Проверка | Статус | Комментарий |
|---|----------|--------|-------------|
| 2.1 | Тендеры привязаны к workspace (`workspace_id`) | ✅ | `tenders` имеет `workspace_id`, уникальность `(workspace_id, source_id, external_id)` |
| 2.2 | Все запросы фильтруют по workspace текущего пользователя | ⚠️ Не проверено | Нет HTTP-слоя — фильтрация не реализована. **Критично для прод.** |
| 2.3 | Нет cross-workspace утечки через ID перебор | ⚠️ Риск | UUID снижает риск, но без фильтра `workspace_id` — прямой доступ |
| 2.4 | CRM-элементы, согласования, расчёты изолированы по workspace | ⚠️ Схема поддерживает | Таблицы имеют `workspace_id`; запросы без фильтра — утечка |
| 2.5 | Seed-данные в одном workspace | ✅ | `seed-data.ts` — единый `workspaceId` |

**Рекомендация:** middleware должен извлекать `workspaceId` из JWT claims и добавлять в каждый запрос к БД. Не передавать `workspaceId` от клиента.

## 3. Аудит действий

| # | Проверка | Статус | Комментарий |
|---|----------|--------|-------------|
| 3.1 | Аудит-лог записывается для ключевых действий | ✅ | `AuditSink` + `withAudit` используются в approvals, CRM, ads, queue |
| 3.2 | Аудит покрывает: решения, подписи, подачу, переходы CRM, показы баннеров | ✅ | Проверено тестами `audit.test.ts` |
| 3.3 | Аудит не блокирует основной flow при сбое записи | ✅ | Очередь: `recordSafely` + тест: audit failure не триггерит retry |
| 3.4 | Аудит-записи immutable (нет UPDATE/DELETE) | ✅ | `audit_log` — append-only; нет endpoint для удаления |
| 3.5 | `actorId` и `workspaceId` в каждой записи | ⚠️ Частично | Домен передаёт `actorId` через ctx; workspace не всегда |
| 3.6 | Аудит хранится отдельно / не удаляем | ⚠️ Рекомендация | Для прод: отдельная schema/таблица с ограниченными правами |

**Рекомендация:** при реализации HTTP-слоя автоматически добавлять `actorId` и `workspaceId` из JWT в каждый аудит-запись через middleware.

## 5. Rate limiting

| # | Проверка | Статус | Комментарий |
|---|----------|--------|-------------|
| 5.1 | Rate limit на API endpoints | ❌ Не реализовано | HTTP-сервер ещё не написан |
| 5.2 | Rate limit на auth endpoints (login/refresh) | ❌ Не реализовано | Auth отсутствует |
| 5.3 | Rate limit на AI-чат (POST /support/chat) | ❌ Не реализовано | Без ограничения — риск расхода токенов LLM |
| 5.4 | Rate limit на поиск тендеров (POST /tenders/search) | ❌ Не реализовано | Без ограничения — спам очереди |

**Рекомендация:** реализовать на уровне middleware (ip + userId): 60 req/min общий; 10 req/min для AI-чата; 5 req/min для поиска. Использовать sliding window (Redis или in-memory для dev).

## 9. Защита от повторной подачи и дублирования задач

| # | Проверка | Статус | Комментарий |
|---|----------|--------|-------------|
| 9.1 | Уникальность тендера: `(workspace_id, source_id, external_id)` | ✅ | Unique index в schema |
| 9.2 | Идемпотентность seed | ❌ Не реализовано | Повторный `npm run seed` даёт дубли |
| 9.3 | Защита от double-submit заявки | ✅ Логика | `authorizeSubmission` — stateful gate; но нет HTTP idempotency key |
| 9.4 | Защита от двойного запуска очереди | ⚠️ Частично | In-memory — single-process; при durable queue нужен distributed lock |
| 9.5 | Идемпотентность платежей | ⚠️ Заглушка | `StubPaymentProvider` хранит intents в памяти; нет реальной защиты |
| 9.6 | Idempotency-Key header в API | ❌ Не реализовано | Для POST-запросов, создающих ресурсы |

**Рекомендация:** добавить `Idempotency-Key` header для `POST /tenders/search`, `POST /approval-requests`, `POST /support/tickets`. Хранить ключ в Redis/DB с TTL 24h.

## 10. Юридические стоп-факторы

| # | Проверка | Статус | Комментарий |
|---|----------|--------|-------------|
| 10.1 | Подача заявки **только после подтверждения человека** | ✅ | `authorizeSubmission` лишь разблокирует; не отправляет |
| 10.2 | КЭП (квалифицированная электронная подпись) — не автоматизирована | ✅ Корректно | Система не подписывает документы; КЭП — на стороне пользователя |
| 10.3 | Платежи — заглушка, нет реальных списаний | ✅ | `StubPaymentProvider` + предупреждение в README |
| 10.4 | Решение об участии (participate/decline) — аудит | ✅ | `tender_decisions` записывает `decidedAt`, аудит |
| 10.5 | Цена не может быть ниже минимальной маржи | ✅ | `assertMinMargin` + `MinMarginViolationError`; тест покрывает |
| 10.6 | Согласование: отказ юриста блокирует подачу | ✅ | `evaluateGate` проверяет rejected; тест покрывает |
| 10.7 | OpenAPI-описание содержит предупреждение о человеческом подтверждении | ✅ | `authorize-submission` description: «НЕ отправляет заявку» |
| 10.8 | Отсутствие автоматической отправки на площадку | ✅ | Нет реального адаптера; `StubTenderSourceAdapter` |
| 10.9 | Аудит юридически значимых действий (решение, подпись, авторизация) | ✅ | Покрыто тестами |
| 10.10 | Запрет на удаление/изменение audit_log | ✅ | Append-only таблица; нет UPDATE/DELETE endpoint |

**Статус:** юридические стоп-факторы **соблюдены на уровне foundation**. При реализации HTTP-сервера — не добавлять автоматическую подачу заявки без явного действия пользователя.
